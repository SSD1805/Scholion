# Production release key ceremony

This runbook defines the **human-controlled boundary** for Scholion's production Ed25519 release-signing key.

Scholion's installed application receives only public verification material. The private release-signing key is never an application resource, repository secret, CI input, fixture, build artifact, issue attachment, chat paste, or ordinary developer convenience file.

Issue #177 owns this ceremony. Issue #168 consumes only the reviewed public `update-keys.json` plus externally produced signatures.

## What this key does

The Scholion Ed25519 release key signs the exact update-manifest payload bytes produced by `scripts/build_release_metadata.py payload`.

It does **not** replace Windows code signing or macOS Developer ID signing/notarization. Those are separate OS trust systems tracked by #173.

The three trust identities therefore remain distinct:

1. Scholion Ed25519 release key: signs Scholion's own release metadata.
2. Windows code-signing identity: authenticates Windows application/installer artifacts to Windows.
3. Apple Developer ID identity: authenticates the macOS application to Gatekeeper; Apple notarization is a separate direct-distribution service check.

## Ceremony environment

Generate the production Ed25519 keypair in an environment you control **outside the Scholion repository tree**.

Before generation:

- choose the key-generation/signing tool deliberately and record its exact name/version;
- confirm it supports Ed25519 key generation, public-key export as SubjectPublicKeyInfo DER, and exact-message Ed25519 signing;
- choose private-key custody and recovery before creating the key;
- ensure the private-key location is not inside a Git worktree, cloud-synchronized project folder, CI workspace, or application data directory; and
- decide who, if anyone, can recover or rotate the key if the primary copy is lost.

Do not use an RFC/test key, repository fixture, throwaway development key, or a key generated by an ephemeral assistant/runtime as production trust.

## Private-key custody

The private key must remain external to Scholion's repository and application lifecycle.

Acceptable custody should provide deliberate access control and recovery. Depending on the chosen tooling/environment, that may be an encrypted offline file, hardware-backed key, dedicated removable medium, or another reviewed mechanism. The exact mechanism is a release-operations decision, not application code.

At minimum:

- keep the primary private key outside the repository;
- protect it with the strongest practical access control supported by the chosen tool;
- maintain a deliberate recovery copy or documented no-recovery decision;
- do not upload it to GitHub Actions secrets merely to make release automation convenient;
- do not paste it into issues, PRs, logs, documentation, chat, or support channels; and
- never publish private-key bytes, seed material, recovery material, or an export containing them.

## Public-key handoff

Only the public key crosses into Scholion's release-review workflow.

Export the Ed25519 public key as an RFC 8410 SubjectPublicKeyInfo DER document. Scholion's builder intentionally accepts that public-key-only container rather than arbitrary raw 32-byte input. This makes accidental handoff of a raw Ed25519 seed/private scalar less likely.

Build the production catalog with:

```bash
python scripts/build_update_key_catalog.py \
  --current-key-id release-2026-a \
  --current-public-key-der /path/to/public-key.der \
  --output /path/to/update-keys.json
```

For a later rotation overlap, provide both `--next-key-id` and `--next-public-key-der`. The builder rejects malformed Ed25519 SPKI, invalid IDs, duplicate public keys, incomplete rotation pairs, and catalogs that fail the same strict parser used by #172.

The resulting `update-keys.json` is public verification policy and may be reviewed/committed through the normal release process. The private key must not accompany it.

## Public catalog review

Before approving the catalog:

1. confirm the key ID follows the bounded lowercase Scholion convention;
2. independently confirm the exported public key belongs to the intended private key using the chosen signing tool;
3. review the generated `update-keys.json` bytes;
4. validate the catalog through the #172 release-trust preparation path; and
5. record only public identity and sanitized ceremony evidence.

A first release normally contains exactly one `current` key. Rotation later may contain one `current` and one `next` key according to the overlap contract in `production-trust-inputs.md`.

## Production-shaped signing proof

After the real key exists, qualification needs one production-shaped signature without giving CI the private signer.

1. Build exact payload bytes with `scripts/build_release_metadata.py payload`.
2. Transfer those exact bytes to the controlled signing environment without modification.
3. Sign the exact payload bytes with the production Ed25519 private key.
4. Export only the raw 64-byte Ed25519 signature back to the release workspace.
5. Wrap it with `scripts/build_release_metadata.py envelope` using the approved key ID.
6. Verify that Scholion's native verifier accepts the exact payload/signature/key and rejects mutation, wrong key IDs, malformed signatures, and altered payload bytes.

The private key stays in the controlled signing environment throughout.

## Rotation and compromise

Rotation is an application-release event.

- Ship a release containing both the current and next public keys before metadata begins using the next key ID.
- Only after supported clients trust the next public key should the signer move to it.
- Removing an old public key requires a later signed application release.
- Never reuse a manifest sequence for different bytes or a different key.

A compromised current key cannot securely teach a client a replacement key if that client trusts only the compromised key. Treat compromise as an incident requiring an explicit recovery plan, not an ordinary metadata edit.

## What completion means

#177 is complete only when:

- the real production private key has been generated under deliberate external custody;
- its recovery/rotation approach is documented privately enough to avoid leaking secrets while still being operationally usable;
- the corresponding public SPKI DER has produced a reviewed `update-keys.json`;
- that catalog passes Scholion's strict #172 custody tooling; and
- a production-shaped external signature has been verified end to end without exposing the private key to Git, CI, the application, or published artifacts.
